# System specification

## Scope and terminology

The application displays Hello World with a color selection in browser pages, a Windows Electron window and Chromium/Firefox sidebars. [PROJECT](PROJECT.md) owns scope, [ARCHITECTURE](ARCHITECTURE.md) owns the platform arrangement and [DECOMPOSITION](DECOMPOSITION.md) identifies C1-C9 responsibility owners. A UI instance is one page, desktop window or sidebar document. A sidebar session lasts from opening until closing; tab switches and focus changes while open do not start another session.

## Controller and lifecycle boundaries

C2 exposes a mount operation for a valid application document and returns reset and dispose functions. Mount establishes R1; reset reasserts the checked/color pair; disposal removes owned listeners. Calling reset repeatedly is idempotent. Ignore unsupported selection inputs without leaving a mismatching pair. No script supplied by a user is evaluated.

The Chromium adapter uses a named runtime connection and a panel-ready message containing a valid integer window ID. The worker checks the sender belongs to its own extension and panel entry before registering it. A reset message identifies the target window and current opening session; the panel ignores wrong-window, malformed and obsolete-session messages. Connection loss cleans routing entries; reconnection alone does not reset an unchanged open session. Opening/closing notifications take precedence over an older ready/reset exchange. A page attaching after an opening must start red; a retained page reconnecting after a close/open must consume the latest reset. Duplicate opening/closing notifications are harmless. These are adapter contracts, not new persistent data or application controls.

Firefox document disposal follows the native sidebar lifecycle. Browser page restoration must invoke controller reset after native form restoration. Electron startup and resource lookup failures produce a diagnostic and a failing launch/build result; packaging may not disguise an absent entry as a valid empty window. Build tools report actionable sanitized errors with a nonzero exit and preserve unrelated outputs. No product error dashboard, import/export or recovery UI is introduced.

| Group | Objective scenarios | Required evidence |
| --- | --- | --- |

| A2 Layout and restoration, R3-R4 | 200, 320 and 1200 CSS-pixel widths; 200 percent zoom; short viewport scroll; reload/history restore; two independent instances | Geometry/accessibility assertions, focus checks and inspected rendered screenshots; restoration and independence assertions |
| A3 Desktop, R4,R6,R9 | Fresh startup entry, final-window quit, fresh relaunch, restricted renderer and resource paths; complete Windows distribution in a path containing spaces | Actual Windows launch when a facility exists; otherwise feasible host-side entry/asset/security/path tests, PE architecture/resource and archive checks, with native execution explicitly untested |
| A4 Chromium, R4,R7 | Load extracted package; open, change, close/reopen; tab/focus/resize preservation; two windows; fresh/retained documents; worker restart, reconnect and stale messages | Adapter success/race/failure tests plus actual full-browser extension events where available; a plain tab loading the panel document does not establish native lifecycle acceptance |
| A5 Firefox, R4,R8 | Load extracted temporary add-on; open, change, close/reopen; two windows; reload and restart semantics | Manifest/package checks, shared-page behavior and actual Firefox extension loading/sidebar checks where available; modeled unload evidence is labeled separately |
| A6 Distribution, R5,R9-R10 | Clean builds, relative asset paths, offline runtime resources, runtime checksum failure and unsafe ZIP rejection; cumulative archive set and uploaded-byte equality | Extract and inspect the actual final archives, execute feasible checks against extracted content, record SHA-256/version/source identities and read back release assets |

Tests run under pytest. Browser checks follow repository BROWSER_DEV_POLICY.md and Playwright guidance: dedicated binaries/profiles, Chromium primary and Firefox included, headless shell for ordinary UI checks when sufficient. Full Chromium is a separate requirement for native Chromium extension checks, even when run headless. Identify the actual runner/build/mode. Establish representative repeated interaction/render/teardown before dependent suites.

Unavailable native Windows execution and full-browser modes are outside the current verification scope under repository policy after bounded diagnosis/recovery. Their absence does not block feasible packaging or later platform delivery; record excluded scenarios without claiming them passed or removing their product contracts. Actual feasible build or application failures remain blockers. Source/manifest inspection cannot be reported as native installation or lifecycle success. Browser support beyond observed versions is not claimed.

## Exclusions and sources

No persistent selection, accounts, backend, file operations, cookie/URL settings, installer, auto-update, signing or store submission is required. Platform differences may change hosting and lifecycle only, preserving common controls and color semantics.

Architecture's [platform references](ARCHITECTURE.md#platform-references) supply API, security and packaging sources. [Firefox temporary loading](https://extensionworkshop.com/documentation/develop/temporary-installation-in-firefox/) documents its development-installation limitation. Platform references were inspected on 2026-10-27; implementation must retain exact tested runtime identities.
